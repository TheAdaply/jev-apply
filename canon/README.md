# canon — the canonical question bank

Generated by `scripts/canon-cluster.mjs` from `corpus/` (docs/PLAN.md §2.7). Question text only:
every label here is public form text an employer publishes, and nothing in this directory is
personal data. The user's *answers* live outside the repo, in `~/.config/jev-apply/`.

## What is here

| file | what it is |
|---|---|
| `questions.yaml` | the bank: 292 canonical questions, each with `surface_forms`, `options_seen` and `frequency` |
| `families/<family>.yaml` | the screening layer for one of the 20 job families (20 files, 256 rows) |
| `vocab/<qid>.yaml` | option alias maps for questions whose vocabulary differs between forms (38 files) |
| `templates/<company>.yaml` | the ordered canonical ids one employer's form uses (29 files) |
| `proposals.yaml` | 64 clustered questions that did not clear a promotion rule — the human review queue |

A row in `questions.yaml`:

```yaml
- qid: q.auth.sponsorship_future        # stable id; the prefix is the layer
  text: Will you now or in the future…  # canonical phrasing
  layer: auth                           # core | auth | legal | comp | eeo | narrative | screening | company
  type: single_select                   # the control it usually arrives as
  answer_shape: yes_no
  kind_default: rule                    # constant | rule | policy | narrative | company | never
  surface_forms: [{label: …, count: 30, ats: [greenhouse]}]
  options_seen: [{options: [Yes, No], count: 24}]
  frequency: {total: 120, postings: 118, by_ats: {…}, by_family: {…}}
```

`kind_default: never` (EEO, salary history) is never auto-filled — see AGENTS.md.

## How it was built

400 build-set postings (7090 question instances; the 100 hold-out postings in
`corpus/holdout.txt` were not opened) → 938 normalized labels → four passes:

1. **exact** — the alias table in `src/canon/normalize.mjs` resolved 100 label groups for free.
2. **Jev pass 1** — "which canonical question is this an instance of, or is it new?" matched 518 more.
3. **Jev pass 2** — the 320 new questions were clustered against each other; 49 merged.
4. **Jev pass 3** — a question a family asked only once joins that family's screening layer only when
   Jev judges it durable screening (81 of 135); the rest wait in `proposals.yaml`.

Conditional follow-ups ("If yes, please explain") never join their parent's canonical question —
49 of them keep their own row with a `dependency` on the field asked before them,
because filling one with the parent's answer would be a wrong answer, not a missing one.

Jev spent 171 requests / 4153k input tokens
(≈ $0.17) in 21 s.

Jev only ever *selected* (`choice` with an explicit `none_of_these`, refused below confidence
0.7); every id and canonical text is a deterministic slug minted in code.

Promotion rules (`RULES` in the script):
- **core** — asked across ≥ 8 job families by ≥ 2 employers.
- **family screening** — recurs inside one family (≥ 2 postings, or ≥ ⅓ of the question's instances).
- **company** — one employer's question, on ≥ 3 of that employer's postings.
- **template** — ≥ 3 postings from one employer sharing ≥ 80% of their canonical ids.
- anything else stays in `proposals.yaml`.

## Regenerate

    node scripts/canon-cluster.mjs            # needs TYPESAFE_API_KEY
    node scripts/canon-cluster.mjs --dry-run  # alias pass only, no model calls

Re-running rewrites every file in this directory.

## Coverage

Measured separately, on the hold-out postings this build never opened, by
`node scripts/canon-eval.mjs` — which writes its table to `canon/eval-<YYYY-MM-DD>.md` beside this
file. Each bucket carries **mapped** (the bank recognised the field) and **answerable** (mapped
*and* that canonical question has an answer the user can pre-compute); PLAN §2.7's targets — core
≥ 95%, screening ≥ 85%, narrative ≥ 80% — score the answerable column. The newest `eval-<date>.md`
in this directory is the current measurement.

`eval-2026-09-22.md`, the full hold-out — 100 of 100 postings, 1946 question instances, 322 Jev
requests (3.22 per posting):

| group | instances | answerable | target |
|---|---:|---:|---:|
| core | 1407 | 98.5% ✓ (98.6% mapped) | 95% |
| screening | 74 | 64.9% ✗ | 85% |
| narrative | 56 | 51.8% ✗ (91.1% mapped) | 80% |
| overall | 1946 | 78.3% (79.5% mapped) | — |

Core clears its target. Narrative is recognised on 91.1% of its instances but only half of that is
pre-answerable: the gap is `q.narrative.why_company`, a `company`-kind question written per posting
at queue time by design. Screening misses because a screening row is only a candidate when its
`family` equals `classifyTitle(posting.title)`, so a question the bank filed under another family
cannot map. Two buckets sit outside the targets on purpose: `eeo` (349 instances, 0% — demographic
fields are never put in front of the selector, exactly as the runner skips them) and `company`
(60 instances, 100% — mapped, and answered at queue time).
